# THA Governing Architecture

**This directory is the single canonical home for The Healthy Apples' governing architecture.**
Established 2026-06-30 (GOV-AI1). Architecture documents no longer live in `docs/investigations/` — investigation files there are point-in-time analysis and history only.

Anything in this directory is **governing**: required reading before significant implementation, and enforced by the Architecture Compliance Checklist in `ENGINEERING_WORKFLOW.md`.

> **Architecture Bootstrap (mandatory entry point).** This README is the first thing to read before any significant investigation, recommendation or implementation. The documents listed below are the governing architecture; every proposal and implementation must comply with them. If a proposed change conflicts with the governing architecture: **STOP, explain why, and do not continue until approved.** This bootstrap is enforced as STEP 2 of `ENGINEERING_WORKFLOW.md` (added GOV-AI2, 2026-06-30).

> The Platform Knowledge Completion Architecture is the governing source for **how every knowledge domain THA ships must grow**: one graduation pipeline (candidate → gate → confirm → publish, with rejection as a first-class terminal state), one layered evidence chain, one owner and one "mouth" per knowledge type, and one stated completion criterion per domain. Promoted under `EWO-PKCA1` (2026-07-03), it named a shape THA had already built correctly four separate times without noticing it was one shape. **Extended under `PKR3` (2026-07-11) to admit a fifth domain: Product Knowledge — the canonical knowledge describing The Healthy Apples itself — alongside Food, Nutrition, Recipes and Household Knowledge**, with the Product Knowledge Registry (below) as its canonical owner. `PKR3` creates **no new governing architecture**: Product Knowledge fills a row in every table the document already had (§1.1 pipeline, §2.1 one-mouth, §3.1 MVF, §6.1 completion, §7 roadmap) and invents no lifecycle of its own — which is the clearest evidence available that the generalisation was real. What it adds is the domain's own character (§4.3, §9): Product Knowledge is the platform's **first self-describing knowledge domain**, where the subject and the source are the same system — so the evidence chain inverts. A food fact is wrong because it was *never* true; a product fact is wrong because it *stopped* being true. Fabrication is nearly impossible; **staleness is the whole risk**, and a stale entry is indistinguishable from a fresh one by reading it. Hence **Rule KC14** (for a self-describing domain, *currency* is the evidence standard — `last_verified` and a named owner accountable for it being true *now*), **Rule KC13** (`visibility` is part of the MVF bar and fails closed — the first domain where a missing field is a *security* defect, not an invisible fact), **Rule KC12** (a declined discovery is *recorded*, or every future audit rediscovers it and re-asks the same question forever), and **Rule KC15** (maintenance is not a follow-up; it *is* the work — Product Knowledge decays by default and no other knowledge domain does, which is why updating the registry is a Definition of Done item in `ENGINEERING_WORKFLOW.md`). It names the domain's declared-vs-enforced gap (Rule KC8) **on the day the domain is created** — currency, visibility, and prose↔inventory bijection are today entirely unenforced — rather than months after it started costing something, as §4.1's Layer 2 gap was. And it fixes the load-bearing distinction: **investigations discover; the registry owns; implementations maintain.** Discovery without transfer of ownership is the failure THA has repeated for three years — something is found, written down beautifully, read once, and never maintained, so the next person to ask finds it out again (Risk R7). Phase 7 of the roadmap exists so the forthcoming **Platform Discovery & Experience Audit** has a canonical destination for everything it discovers, and a gate that fails it if its findings stay inside itself.

> The Product Knowledge Registry Architecture (`PKR1`, 2026-07-11) is the governing source for **knowledge about The Healthy Apples itself** — the question none of the other architectures answers. Platform governs how THA is built; the Source of Truth Register governs which store owns which fact; Intelligence governs how THA reasons; Experience governs how a person encounters THA; UI governs how THA looks. None of them holds the list of what THA *is*: its domains, pages, routes, journeys, capabilities, hidden and admin surfaces, dialogs, integrations, settings, claims, benefits, glossary, and screenshots. That knowledge is currently reconstructed from code and 380+ investigations on every ask, and is never retained. The registry becomes its single owner, under one governing distinction: **investigations discover; the registry owns.** An investigation is history the moment it is written and is never edited; a registry entry is present-tense, carries a named human owner, and is *corrected* rather than superseded — staleness in it is a defect, not drift. It cites Data, Intelligence, Experience, and UI ownership and restates none of it, and it is a description, never a dependency: no runtime code may read it. It defines 28 canonical sections and the folder structure they will occupy beneath `docs/product/` — **which it deliberately does not create or populate.** Enhanced by `PKR2` (2026-07-11) with the three principles that make the registry a platform asset rather than a filing system: **Permission-Aware Product Knowledge** (§11) — one truth, four audiences (`public` · `household` · `admin` · `developer`), monotonic and cumulative, keyed on *role* and never on subscription tier, because knowing what premium does is not access to it; the registry *classifies* what each audience may be told and **never authorises** — `server/lib/access.ts` remains the sole authority on who anyone is, so that a Markdown edit can never become a privilege escalation. **The Registry as Companion Knowledge** (§12) — the Companion *queries* the registry and may never duplicate product knowledge into a prompt, template, or fallback string; it enters the platform as a registered Knowledge Capability composed through INT17, which keeps its ownership of every byte the model reads; filtering happens before composition, never by asking the model to withhold what it has been shown; and the Companion never explains an absence, because acknowledging withheld content discloses the fact the tier protected. **Engineering Governance** (§16) — `PKR2` amends the `PKR1` boundary that forbade any runtime read (now *read, never obeyed*: Intelligence may read it, no code may branch on it), and wires the Definition of Done obligation into `ENGINEERING_WORKFLOW.md` (a mandatory **Product Registry Impact** section, a **Product Registry Compliance** block, and a Completion Gate step) and the implementation template — so every user-facing implementation must update, add, or retire the affected entries **in the same change**, by default rather than by memory. The cost of that read path is stated plainly rather than buried: under `PKR1` a stale entry misled a reader who went looking; under `PKR2` it is read aloud to a household in the Companion's voice, and the Companion will always be more convincing than the registry is accurate. **`PKR3` (2026-07-11) places this document under the platform-wide law:** the registry is named the **canonical owner of the Product Knowledge domain** in the Platform Knowledge Completion Architecture (§9), on exactly the footing NK1/NK2 hold for Nutrition and FS1/FS2 hold for Recipes — the domain's own architecture, subordinate to the general one, corrected if the two ever conflict. `PKR3` adds no rule to this document and restates not one line of it; it *cites* it, because restating it would create the second owner Rule PKR13 forbids, in the document that admits the rule. The registry is still **defined here and populated nowhere**: `docs/product/` does not exist, and `PKR3` deliberately does not create it.

> The Experience Architecture (EXP1, 2026-07-10) is the governing source for how people experience THA — the timeless, technology-independent principles (Home as the emotional centre, progressive disclosure, calm before capability, one primary action, and the rest) plus the UX Governance Checklist every user-facing implementation must pass. It is the general law of which the Intelligence Discovery & Presentation Principle and the Companion Card Experience Principle (indexed under Intelligence Governance above) are the Intelligence-specific faces; it does not alter them or any ownership boundary. The UI Architecture (UIA2, 2026-07-10, from the approved UIA1 discovery) is its visual constitution — the governing source for how THA looks: the Calm Orchard Visual Language, visual hierarchy, colour/typography/spacing/motion law, Brand Identity Architecture, Visual Trust, one-owner-per-visual-concern with retire-on-introduction, and the UI Governance Checklist. It is subordinate to the Experience Architecture: Experience governs behaviour, UI governs presentation, and Experience prevails in any conflict.
>
> The Experience Architecture was **enhanced by `EXP2` (2026-07-11)** with the **Premium Experience Principles** (§ 17) — a lens over Experience Principles 1–8 governing the *standard of craft* to which they must be done, never a rival set of principles — and the Premium Standard block of its UX Governance Checklist (§ 18). Premium in THA is defined as *the perceptible result of care taken on the household's behalf*: not ornament, density, motion, or expense, and explicitly **not exclusivity** — it is the quality every household receives, including the ones who pay nothing. Its test: *if the household would not feel the care, it is decoration; if they would feel its absence, it is craft.*
>
> **Both documents became enforceable on 2026-07-11 (`ARCH-VERIFY1`).** Until then, each declared that its checklist *"stands beside the Architecture Compliance Checklist in `ENGINEERING_WORKFLOW.md`"* — while `ENGINEERING_WORKFLOW.md` had never referenced either document, leaving both checklists unreachable by anyone actually following the workflow. The **Experience & UI Governance Compliance** block now makes them mandatory for every user-facing implementation, and the Architecture Bootstrap (STEP 2) now names them as required reading. Where the Experience Architecture is the **law** of the user-facing layer and the UI Architecture is its **visual constitution**, the Product Knowledge Registry is its **census** — the enumeration of surfaces without which Experience Principle 6 (*one canonical place for everything*) was never checkable.
>
> The Experience Language (`EXPLANG1`, 2026-07-15) is the governing source for **how THA must *feel***. If the Experience Architecture governs what the experience must *do* and the UI Architecture governs how it must *look*, the Experience Language governs the **feeling those two exist to produce** — THA's emotional architecture, stated as emotion so a person can check for it. It is the **emotional constitution**: subordinate to the Experience Architecture (behaviour prevails over a description of feeling, because a feeling is produced by behaviour and presentation, never decreed) and a sibling to the UI Architecture (which owns the look, including the motion vocabulary, and which the Experience Language never overrides and is never overridden by). Its purpose is to catch the gap no checklist can: a change can pass every box on both governance checklists and still feel cold, theatrical, cluttered, or slippery — because a checklist verifies that rules were followed, not that a feeling was produced. It defines the seven feelings THA must produce (calm · welcoming · effortless · intelligent · reassuring · premium · quietly memorable) *without becoming theatrical, gimmicky or distracting*; thirteen **Principles of Feeling** (each with why it exists, how users should feel, practical implications, and things to encourage/avoid); the canonical six-beat **Experience Rhythm** (Arrival → Orientation → Confidence → Action → Understanding → Completion) applied to every realm; the **Experience Review Questions** (§ 6) every implementation is evaluated against before it is complete; and the **Experience Anti-Patterns** (§ 7) THA must never adopt. It restates neither the eight Experience Principles nor the eight UI Principles — restating a rule creates a second owner of it — and it creates **no** colour, component, token, route, or runtime dependency. Its Review Questions stand beside the two checklists in the Experience & UI Governance Compliance gate; where any conflict of *rule* remains, it resolves upward to the Experience Architecture. It was **enhanced by `EXPLANG1A` (2026-07-15)** with **§ 4A — The Place Principles**: eight arrival-derived principles of feeling (The THA Promise · THA is a place · Arrival before work · Walking, not scrolling · The application shell is constant · Light has meaning · Home is not the dashboard · Premium through restraint), discovered during the ARRIVAL1 experience prototype and admitted by governance. They frame THA as a *place a household arrives in and moves through* rather than a set of pages, deepening the thirteen Principles of Feeling without renumbering or restating any of them; the enhancement extended § 6 and § 7 only where a new principle genuinely required an additional check.

## Compliance

Every significant implementation must pass the **Architecture Compliance Checklist** in `ENGINEERING_WORKFLOW.md`.

Every **AI-related** implementation must additionally pass the **AI ARCHITECTURE COMPLIANCE** block in `ENGINEERING_WORKFLOW.md`, which confirms it uses the canonical Intelligence Platform, the Capability Registry, and the Intent Engine; reuses existing business services; creates no second assistant; duplicates no conversation state; uses registered capabilities only with permission-aware access; and produces honest gaps rather than fabricated knowledge.

Every **user-facing** implementation must additionally pass two blocks in `ENGINEERING_WORKFLOW.md`:

- **EXPERIENCE & UI GOVERNANCE COMPLIANCE** — which requires the **UX Governance Checklist** (`THA_EXPERIENCE_ARCHITECTURE.md` § 18, including its Premium Standard block) and the **UI Governance Checklist** (`THA_UI_ARCHITECTURE.md` § 18) to be completed in full, with any conflict between them resolved in the Experience Architecture's favour.
- **PRODUCT REGISTRY COMPLIANCE** — which requires every affected Product Knowledge Registry entry to be created, updated, or retired **in the same change** (`PLATFORM_KNOWLEDGE_COMPLETION_ARCHITECTURE.md` Rule KC15).

Every implementation that adds, changes, or retires a **client-side building block** (a component, hook, token, utility class, or shared pattern) must additionally pass:

- **ADOPTION REGISTER COMPLIANCE** — which requires every owner created, adopted, or retired to be recorded in the **Platform Experience Adoption Register** (`docs/implementation/ux/ADOPTION_REGISTER.md`) **in the same change**, and `npm run adoption:check` to pass (`THA_UI_ARCHITECTURE.md` § 17). *Added under `PX1-W5` (2026-07-13).* UIA § 17 has always mandated this register — *"authored-but-unadopted must be impossible to hide"* — and for as long as it did not exist, that sentence was the only rule in the governing architecture with **no owner and no way to check it**. `PX1` found the consequence: `hover-elevate` consumed by every control and defined nowhere; `prefersReducedMotion()` with zero consumers; `PageHeader.tsx`, a complete unadopted successor to `WorkspaceHeader`, sitting live-looking in the tree. The register is operational, not architectural: it adds no law, and makes the existing law checkable.

**If any check fails: STOP, explain why, do not continue.**

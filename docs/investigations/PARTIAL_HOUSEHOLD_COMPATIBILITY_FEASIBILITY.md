## Background

The proposed THA behaviour adds a reviewable adaptation layer to meal planning:

> "Beef Lasagne fits 3 of 4 household eaters. Lilly requires:
> beef mince → Quorn mince, standard pasta → gluten-free pasta"

The question is whether the existing architecture already supports this reasoning, or whether new systems are required.

## Data Flow Diagram

```
matchMealsForHousehold(userId, weekId)
  │
  ├── loads household_eaters rows (all members including adults)
  ├── resolves effective diet profile per eater (defaultDietTypes + overrides)
  ├── joins user_preferences for adult eaters (excluded ingredients, preferences)
  │
  └── for each mealTemplate → scoreTemplate(template, members, settings, swapMap)
        │
        ├── assembles allSlotIngredients from template slot arrays
        │     sharedBaseComponents + proteinSlots + carbSlots + vegSlots + toppingSlots + sauceSlots
        │
        ├── for each member:
        │     ├── DIET PATTERN CHECK:
        │     │     if template.compatibleDiets does not include member's diet
        │     │     → push `"${diet} diet not covered"` to member swaps
        │     │
        │     └── INGREDIENT EXCLUSION CHECK:
        │           for each allSlotIngredients:
        │             if ingredient matches member.excludedIngredients
        │             → lookup swapMap (ingredient_swaps DB table)
        │             → push `"${ingredient} → ${healthier}"` OR `"remove ${ingredient}"`
        │
        ├── builds MemberChange[] { displayName, userId, swaps[] } per eater needing change
        ├── counts membersNeedingVariant
        ├── generates explanation: "Fits 3 of 4 profiles"
        └── returns MealMatch { template, memberChanges, fitScore, scoreBreakdown, explanation }

BACKEND PIPELINE:
  matchMealsForHousehold() → MealMatch[]
      │
      └── smart-suggest-service.ts: selectShellRecoveryCandidate()
            ├── uses match.scoreBreakdown.compatibility to FILTER shells
            ├── uses match.template slot ingredients to assemble candidates
            └── DISCARDS memberChanges — not forwarded downstream

API RESPONSE → client:
  SmartSuggestEntry { candidate: SmartCandidate, explanation: MealExplanation }
      ├── SmartCandidate: NO memberChanges field
      └── MealExplanation: { title, reasons[], scoreBreakdown } — NO household fit data
            reasons[] generated by generateMealExplanation() from USER preferences only
            NO per-eater conflict data included

CLIENT UI (weekly-planner-page.tsx):
  Receives SmartSuggestResult → renders meal cards
  memberChanges data: NEVER RECEIVED — gap at API boundary
```

### Q1 — Can THA determine which eaters are compatible / incompatible for a given meal?

**YES — fully capable at the backend.**

`scoreTemplate()` iterates every household eater and builds a per-eater result.

**`MemberChange` interface — `server/lib/household-meal-matcher.ts:35–39`:**
```typescript
interface MemberChange {
  userId: number | null;
  displayName: string;   // ← named eater
  swaps: string[];       // ← their specific required changes
}
```

**`MealMatch` return type — `server/lib/household-meal-matcher.ts:51–60`:**
```typescript
export interface MealMatch {
  template: MealTemplate;
  sharedIngredients: string[];
  memberChanges: MemberChange[];  // ← per-eater compatibility results
  swapsNeeded: string[];
  extraPrepMinutes: number;
  fitScore: number;
  scoreBreakdown: ScoreBreakdown;
  explanation: string;
}
```

**Per-eater processing loop — `server/lib/household-meal-matcher.ts:262–293`:**
```typescript
for (const member of members) {
  const swaps: string[] = [];
  // ... conflict detection ...
  if (swaps.length > 0) {
    membersNeedingVariant++;
    memberChanges.push({ userId: member.userId, displayName: member.displayName, swaps });
  }
}
```

Eaters with no conflicts produce no `MemberChange` entry — the compatible/incompatible split is implicit in whether a named entry exists in `memberChanges`.

### Q2 — Can THA determine WHY an eater is incompatible?

**YES — two distinct conflict detection paths, both recording the specific reason.**

#### Path A: Dietary pattern conflict (`server/lib/household-meal-matcher.ts:269–276`)
```typescript
const templateDiets = template.compatibleDiets ?? [];
if (templateDiets.length > 0 && member.dietTypes.length > 0) {
  for (const diet of member.dietTypes) {
    if (!templateDiets.includes(diet)) {
      totalDietConflicts++;
      swaps.push(`${diet} diet not covered`);
      // e.g. "Vegetarian diet not covered", "Gluten-Free diet not covered"
    }
  }
}
```

#### Path B: Ingredient exclusion conflict (`server/lib/household-meal-matcher.ts:280–287`)
```typescript
const excluded = member.excludedIngredients.map((e) => e.toLowerCase());
for (const ingredient of allSlotIngredients) {
  const key = ingredient.toLowerCase();
  const isExcluded = excluded.some((ex) => key.includes(ex) || ex.includes(key));
  if (isExcluded) {
    const healthier = swapMap.get(key);
    swaps.push(healthier ? `${ingredient} → ${healthier}` : `remove ${ingredient}`);
    // e.g. "beef mince → lentils", "remove ricotta cheese"
  }
}
```

**Important distinction:** Path A detects dietary category mismatches (soft conflicts). Path B detects explicit ingredient exclusions (hard restrictions). They are independent checks and can both fire for the same eater. Path A does NOT resolve to specific ingredients — it flags the category mismatch only. Path B is ingredient-specific.

### Q3 — Does THA contain substitution intelligence?

**PARTIAL — pre-defined keyword rules plus a DB swap table. No AI or semantic reasoning.**

#### Hardcoded rules per diet goal — `server/lib/recipe-swap-engine.ts:39–140`

```typescript
const VEGETARIAN_RULES: RuleRow[] = [
  ["beef",    "lentils",        "plant-based protein swap"],
  ["mince",   "lentils",        "plant-based protein swap"],
  ["chicken", "chickpeas",      "plant-based protein swap"],
  ["pork",    "tofu",           "plant-based protein swap"],
  ["bacon",   "smoked tofu",    "plant-based protein swap"],
  // ...
];

const KETO_RULES: RuleRow[] = [
  ["pasta",     "courgette noodles",  "low-carb alternative"],
  ["spaghetti", "courgette noodles",  "low-carb alternative"],
  ["rice",      "cauliflower rice",   "low-carb alternative"],
  // ...
];
```

#### DB-backed ingredient swaps — `shared/schema.ts:294–298`
```typescript
export const ingredientSwaps = pgTable("ingredient_swaps", {
  id: serial("id").primaryKey(),
  original: text("original").notNull(),
  healthier: text("healthier").notNull(),
});
```

#### Integration in household matcher — `server/lib/household-meal-matcher.ts:225–229`
```typescript
const swapRules = await db.select().from(ingredientSwaps);
const swapMap = new Map<string, string>();
for (const s of swapRules) {
  swapMap.set(s.original.toLowerCase(), s.healthier);
}
```

**What this can produce today:**
- `"beef mince → lentils"` (if "beef" is in DB swaps and matched by keyword)
- `"remove beef mince"` (if no DB swap entry exists)

**What it cannot produce:**
- `"standard pasta → gluten-free pasta"` (requires a gluten-free swap rule, not a vegetarian one — different diet goal path)
- Contextually intelligent swaps (e.g., ricotta → cashew cream only in a lasagne context)
- Nutritional equivalence checking
- Multi-ingredient substitution reasoning

The `recipe-swap-engine.ts` rules are goal-oriented (vegetarian, keto, etc.) but the household matcher uses only the flat `ingredientSwaps` DB table — the engine's goal-specific rules are not invoked during household matching. Swap coverage depends entirely on `ingredient_swaps` DB population.

### Q4 — Can THA calculate a "3 of 4 eaters compatible" score?

**YES — both as a raw count and as a weighted compatibility ratio.**

#### Raw count derivation (implicit in `memberChanges`)
```
compatible count = members.length - memberChanges.length
```
The "Fits 3 of 4 profiles" phrase is generated explicitly.

#### Explanation string generation — `server/lib/household-meal-matcher.ts:355–361`
```typescript
const variantCount = memberChanges.length;
if (variantCount === 0) {
  phrases.push(`Fits all ${members.length} profile${members.length !== 1 ? "s" : ""}`);
} else {
  const ok = members.length - variantCount;
  phrases.push(`Fits ${ok} of ${members.length} profiles`);
}
```

#### Numeric compatibility score — `server/lib/household-meal-matcher.ts:78–81`
```typescript
function scoreCompatibility(totalDietConflicts: number, memberCount: number): number {
  if (memberCount === 0) return 1;
  return Math.max(0, 1 - totalDietConflicts / memberCount);
}
```
This produces a 0–1 ratio, weighted at 25% of the composite `fitScore`.

#### `ScoreBreakdown` — `server/lib/household-meal-matcher.ts:41–49`
```typescript
export interface ScoreBreakdown {
  compatibility: number;         // 0–1 per household
  sharedBase: number;
  swapSimplicity: number;        // penalises number of eaters needing variants
  timeFit: number;
  costFit: number;
  healthAlignment: number;
  preferenceConfidence: number;
}
```

The full "3 of 4" count, the 0–1 ratio, and the explanation string are all available in `MealMatch`.

### Q6 — Can THA identify exact ingredients responsible for incompatibility?

**YES — for ingredient exclusion conflicts (Path B). PARTIAL for diet pattern conflicts (Path A).**

#### Ingredient exclusion path (Path B) — exact ingredient names recorded

The matcher iterates `allSlotIngredients` from the template's slot arrays:

```typescript
const allSlotIngredients = [
  ...(template.sharedBaseComponents ?? []),
  ...(template.proteinSlots        ?? []),
  ...(template.carbSlots           ?? []),
  ...(template.vegSlots            ?? []),
  ...(template.toppingSlots        ?? []),
  ...(template.sauceSlots          ?? []),
];
```

For a meal with `proteinSlots: ["beef mince", "chicken thigh"]`, if Lilly has `hardRestrictions: ["beef"]`, the conflict produces `"beef mince → lentils"` — the exact template ingredient name is recorded.

#### Dietary pattern path (Path A) — category mismatch only, no ingredient names

Path A checks `template.compatibleDiets` against `member.dietTypes`. If Beef Lasagne has `compatibleDiets: ["Mediterranean"]` but Lilly is `Vegetarian`, the result is `"Vegetarian diet not covered"` — the system does not resolve this to `"beef mince"` as the specific conflict ingredient.

**The ingredient-level resolution only works for Path B (explicit hard restrictions). A vegetarian eater without explicit meat exclusions in `hardRestrictions` would trigger Path A and produce a category-level message, not ingredient-level conflict identification.**

This is the key precision gap: the two paths produce different quality of conflict information.

### Q7 — Does the Meal Shell architecture help?

**YES — it is the architectural foundation that makes household compatibility scoring possible.**

#### Slot-based ingredient structure — `shared/schema.ts:61–67`
```typescript
sharedBaseComponents: text("shared_base_components").array(),
proteinSlots:         text("protein_slots").array(),
carbSlots:            text("carb_slots").array(),
vegSlots:             text("veg_slots").array(),
toppingSlots:         text("topping_slots").array(),
sauceSlots:           text("sauce_slots").array(),
compatibleDiets:      text("compatible_diets").array(),
```

Rather than a fixed recipe, a meal shell is a set of component options. This directly supports the "adaptation" concept: protein can be swapped, carb can be swapped, base is shared.

#### `scoreTemplate` is purpose-built for this — `server/lib/household-meal-matcher.ts:243–338`

The function exists entirely to answer: "how well does this template fit this household, and what changes would each eater need?" It already produces the complete per-eater adaptation map.

#### Shell recovery (Tier-4) already uses household compatibility — `server/lib/smart-suggest-service.ts:335–370`

```typescript
export function selectShellRecoveryCandidate(
  matches: MealMatch[],
  ...
): ScoredCandidate | null {
  for (const match of matches) {
    if (match.scoreBreakdown.compatibility < 1) continue;  // shells with any conflicts excluded
    // ...
  }
}
```

The shell architecture is already integrated into the planning pipeline. The constraint for Tier-4 is `compatibility === 1` (full household fit). The proposed feature would relax this to allow partial compatibility with visible adaptations.

#### Seed data confirms the adaptation concept — `server/seeds/seed-meal-shell-templates.ts`

Shell templates include multiple protein options (plant-based alongside meat), gluten-free carb alternatives alongside standard ones, and `compatibleDiets` declarations. The data model already anticipates household dietary variety.

| Gap | Impact |
|-----|--------|

### Uncertain

| Item | Uncertainty |
|------|-------------|
| `ingredient_swaps` DB coverage | Whether the table has sufficient entries for common dietary swaps (e.g., gluten-free pasta, oat milk) — content depends on seed data |

| Adult eater `hardRestrictions` population | Previous investigation confirmed adult eater rows are created with `hardRestrictions: []` — Path B conflict detection would be silent for adults until eater rows are corrected |
| Swap quality for complex substitutions | `"wheat pasta → gluten-free pasta"` requires a DB entry mapping `"pasta"` to `"gluten-free pasta"` — may not exist or may collide with keto `"pasta → courgette noodles"` |

## Final Verdict

**STATUS A**

> THA already contains most required capability.

The backend can fully answer the question:

> "Beef Lasagne fits 3 of 4 household eaters. Lilly requires: beef mince → lentils."

This is not a hypothetical — the data is computed by `scoreTemplate()` and exists in `MealMatch.memberChanges` on every planning cycle where shell recovery is attempted. The computation includes the eater's name, the specific ingredient or dietary conflict, and the suggested swap.

**The single blocking gap is an API boundary problem, not an architectural one.** The `memberChanges` array is computed, used internally for Tier-4 filtering (`compatibility < 1` check), and then discarded — it is never included in the `SmartSuggestEntry` or `SmartCandidate` returned to the client.

**Secondary gap:** adult household eater rows currently have empty `hardRestrictions` (see `HOUSEHOLD_EATERS_ADULT_PROFILE_DATA_SOURCE_INVESTIGATION.md`). This means Path B conflict detection would produce no results for adult eaters until that data gap is resolved. Path A (diet pattern via `compatibleDiets`) would still fire if templates are populated.

---

## Safest Next Implementation Option

**Add `memberChanges` to `SmartCandidate` and include it in the API response.**

Specifically:
1. Add `householdFit?: { compatible: number; total: number; changes: Array<{ displayName: string; swaps: string[] }> }` to `SmartCandidate` in `client/src/lib/planner-types.ts`
2. In `smart-suggest-service.ts`, when a shell candidate is assembled via `selectShellRecoveryCandidate`, attach the originating `MealMatch.memberChanges` to the candidate
3. For non-shell candidates (Tiers 1–3), `matchMealsForHousehold` is not called — household fit data would be `undefined` for those candidates unless a separate match lookup is added

This approach requires no DB schema changes, no new computation, and no changes to the matching logic. It surfaces data that is already being computed.

**Prerequisite:** Resolve the adult eater `hardRestrictions` data gap (see STATUS B finding in prior investigation) — otherwise the feature would correctly identify children's conflicts but silently miss adult conflicts.

**LOW**

| Risk | Detail |
|------|--------|
| Computation cost | None — `matchMealsForHousehold` is already called for Tier-4; the data exists |
| Schema changes | None required |

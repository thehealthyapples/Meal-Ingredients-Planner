## Verified ownership and current behavior
- Adult self-profile owner: Profile storage (`users` and `user_preferences`, with diet stored in the canonical adult `household_eaters` record per SoT Domain 16). Human profile edit path: authenticated `PUT /api/profile` in `server/routes.ts`.
- Household member/eater owner: `households`, `household_members`, and `household_eaters`, Domain 16. Human child/eater edit path: authenticated `PATCH /api/household/eaters/:eaterId`; the route resolves the caller's active household server-side and rejects eater IDs outside that household. It currently permits an active household member to edit an eater's name, diet types, and hard restrictions.
- Companion's profile binding (`server/intelligence/bindings/profile.ts`, `profile-read-port.ts`, `profile-read-handler.ts`) executes only `read`. Registry metadata lists `add` as supported and the capability as writable, but `executableIntents` is empty and the implementation intentionally returns a gap for writes. This is a metadata/executable-surface mismatch to correct when adding the behavior.
- Companion's household binding (`household-read-handler.ts`) is likewise read-only; `add` and `delete` intentionally return a gap. Existing household API/service remains the owner and can be reused.
- The Companion already has a proposed-action lifecycle and deterministic confirmation tiers (`companion-action-store.ts`, `action-resolution.ts`, `permissions.ts`, `conversation-gateway.ts`). The action path can support a Yes button, but profile/household writes are not bound as Companion intents today.
- `terms-of-service.ts` requires account holders to be 18+. The privacy policy says children have no accounts and an adult responsible for them may record a name and dietary needs. It does not presently disclose storing broader health conditions for children.
- `shared/privacy/consent.ts` has account-level explicit health-data consent for allergies, restrictions, and health goals. Its wording does not explicitly name reported health conditions or condition-informed food suggestions. Trust & Compliance requires consent vocabulary changes when new processing becomes real and an append-only consent ledger.
- `server/privacy/personal-data-registry.ts` exports/erases an adult's linked eater row by `userId`; no-account child eater rows are not included in that adult's `eater-profile` export/erasure step. A child-health expansion therefore needs an explicit household-child data-rights treatment (access/export/correction/erasure and continuity if the adult account leaves) before implementation.
- Current privacy policy promises minimal child data (name and dietary needs). Storing broader child health context changes that promise and requires a versioned disclosure update and an explicit-consent/re-consent path before collection.
- Food Intelligence §5.1 prohibits diagnosis, treatment, and supplement/dosing advice; medical-condition personalization requires separately reviewed scope and methods. User-provided data must stay labelled as reported, not verified. Recommendation results must use reviewed, source-grounded deterministic capabilities; the LLM cannot choose foods or invent nutrient calculations.

## Architecture-compliant implementation shape
1. Keep one Companion, one conversation state, and the existing proposed-action confirmation lifecycle. A chat proposal names the target person, the exact fact and its proposed value; ambiguous targets/facts require a clarification. A No/decline stores nothing. A Yes confirms that exact pending action and invokes the existing Profile or Household owner; the model never writes directly.
2. Adult account holders edit only their own adult health profile. A household adult can update a dependent child record only after identifying the child and confirming the proposed change. Adult A cannot write Adult B's private profile through spouse/household context.
3. Store facts with explicit `reported by household member` provenance and timestamps in the canonical owner for that person; do not duplicate health facts in chat history, Companion state, or a separate assistant memory store. Preserve the current Profile and Household edit surfaces as equivalent correction/removal paths.
4. Keep support food-scoped and evidence-gated. A reported condition is never converted into an app diagnosis. A condition without a reviewed food-support mapping can be remembered only if the consent/purpose permits, then answered with an honest evidence gap. Do not infer deficiency, prescribe treatment, promise that food will correct it, or give supplement/dose instructions.
5. Update the source-of-truth and capability documentation, consent wording/version, privacy disclosure, data subject registry/lifecycle for child records, profile/household write bindings, and tests in the same dev-scope work. Source/method review for each condition-specific recommendation is a separate gate from storing what the household reported.

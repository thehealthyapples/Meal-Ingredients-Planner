DESIGN DECISIONS
──────────────────────────────────────────────────────────────────────────────

1. Why `real` not `integer`?
   Consistent with existing quantityValue, cupboardQuantity fields.
   Allows fractional quantities (e.g. 0.5 kg, 1.5 litres).

2. Why needUnit as text not enum?
   Future-proof. Units are not yet standardised in Pantry.
   API enforces max(32) to prevent abuse. Enum can be enforced later.

3. Why positive().finite() on needQuantityValue?
   Prevents zero, negative, and Infinity/NaN from being stored.
   Null is explicitly allowed to support clearing.

4. Why PATCH scope is only quantity fields?
   Scope constraint from task spec. updatePantryItemQuantity is narrow
   and deliberate — prevents accidental category/name changes via PATCH.
   A broader PATCH can be added in a later task if needed.

5. Why is needQuantityValue required (not optional) in PATCH body?
   PATCH must be an explicit intent — caller must decide whether to set
   or clear. Optional fields in PATCH create ambiguity between
   "don't change" and "clear to null". Both fields must be provided.

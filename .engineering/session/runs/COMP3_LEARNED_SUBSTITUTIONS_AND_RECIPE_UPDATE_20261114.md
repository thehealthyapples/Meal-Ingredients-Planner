## What shipped

1. **Root cause found and fixed — curated replacements were self-rejecting.** `household-dietary-safety.ts`'s `validateAdaptationSafety` re-checks every suggested replacement against the SAME restriction it was offered to satisfy. A replacement phrase ending in punctuation (e.g. "aquafaba (3 tbsp chickpea water per egg)") was never masked at all — `maskRestrictionSubstitutions`'s `\b...\b` anchor cannot match at a non-word phrase edge — so the trailing word ("egg") silently re-tripped its own restriction. Fixed the anchor to a lookaround (`shared/restrictions/restriction-resolver.ts`), which is a strict generalisation of `\b` (identical behaviour when a phrase starts/ends with a letter or digit; newly correct when it does not). A new generic regression test (`server/tests/test-substitution-rules.ts` §26, backed by the new `listAllCuratedReplacements()` export) checks EVERY curated replacement in the library against every restriction it is declared to satisfy — it caught this bug for Worcestershire sauce/beer/hoisin/teriyaki/soy sauce (the widened coverage below) AND three pre-existing, unrelated bugs (shellfish's "king oyster mushrooms", peanut's "sunflower seed satay-style sauce", eggs' two aquafaba phrasings) that predate this session. All four masking gaps closed in `shared/restrictions/restriction-library.ts`.
2. **Widened curated gluten coverage** (`shared/substitution-rules.ts`): new rules for Worcestershire sauce, malt vinegar, beer, barley malt/malt extract, hoisin sauce, teriyaki sauce; extended the existing soy-sauce rule with a tamari strategy (correctly skipped when soy is ALSO restricted, since tamari is soy sauce).
3. **Learned Substitution Observations** (new table + migration `2026-11-14_comp3_learned_substitution_observations`, new store `server/intelligence/conversation/learned-substitution-store.ts`): when a household states its own fix for an ingredient with no curated/community match, it is recorded (idempotent per household, corroboration counted across DIFFERENT households) and surfaced to any other household hitting the same conflict as an explicitly attributed, unverified suggestion — never promoted to the curated list, never presented as a fact the app vouches for.
4. **The FIRST write verb on `meals`** (`server/intelligence/handlers/meals-write-{port,handler}.ts`, `server/intelligence/bindings/meals.ts`): `replace` persists a Companion-offered ingredient swap to the caller's OWN saved copy — forking a system meal to a private row first (mirrors `POST /api/uplift/accept`'s already-shipping fork sequence exactly), editing in place otherwise. Exact-ingredient-string match only; ownership denial mirrors the existing no-existence-leak pattern. Confirmation tier resolves to `"required"` automatically via the existing `confirmationFor()` switch (meals is not an audited capability).
5. **Resolver wiring** (`server/intelligence/conversation/action-resolution.ts`, `conversation-gateway.ts`): when exactly one replacement is "on the table" (one curated/community option, or the household named one outright, or a bare "yes" confirms the single option), `resolvePlannerAdd` now returns a `meals.replace` proposal instead of a clarification — nothing is written until the household confirms the proposal itself, the same button-press every other write already requires. Multiple candidates with a bare "yes" still ask which, never guess. `recentPlannerDietaryCorrection`'s continuation trigger was widened to recognise short affirmatives ("yes", "go ahead", …), not only substitution-naming words.
